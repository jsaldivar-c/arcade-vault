## Critical: this is Next.js 16.3.3, not the Next.js in your training data

`AGENTS.md` (imported above) is auto-regenerated by `next dev` and enforces this: **read the relevant guide under `node_modules/next/dist/docs/` before writing any App Router code.** Do not rely on remembered Next.js APIs/conventions — this project uses genuinely new/changed behavior. Highlights that matter for this repo (full details: `node_modules/next/dist/docs/01-app/02-guides/upgrading/version-16.md`):

- **Async Request APIs are fully async, no sync fallback**: `params`, `searchParams`, `cookies()`, `headers()`, `draftMode()` must all be awaited. Use the generated type helpers — `PageProps<'/route'>`, `LayoutProps<'/route'>`, `RouteContext<'/route'>` (see `app/layout.tsx` for an existing `LayoutProps<"/">` usage). Run `npx next typegen` after adding routes to regenerate these.
- **`middleware` → `proxy`**: the file and exported function are now named `proxy` (`proxy.ts`, `export function proxy(...)`). `middleware` is deprecated; the `edge` runtime is not supported in `proxy`.
- **Turbopack is the default** for both `next dev` and `next build` — no `--turbopack` flag needed (already reflected in `package.json`).
- **`next lint` is removed.** Lint via the ESLint CLI directly (`npm run lint` → `eslint`), which is how this repo is already set up. ESLint uses flat config (`eslint.config.mjs`).
- **`revalidateTag` now requires a second `cacheLife` profile argument** (e.g. `revalidateTag('posts', 'max')`); for read-your-writes semantics use `updateTag` instead.
- **Parallel route slots require an explicit `default.js`** or the build fails.
- `next/image`: `images.domains` is deprecated (use `remotePatterns`), local images with query strings need `images.localPatterns.search`, and several defaults changed (`minimumCacheTTL` now 4h, `qualities` now `[75]` only).

If a guide doesn't cover what you need, search `node_modules/next/dist/docs/` before falling back to prior knowledge.

## Product spec: what's being built

Arcade Vault is a retro-arcade web platform (Spanish-language UI) where users play browser games and compete on point leaderboards. It was originally scaffolded from a static HTML/Babel-in-browser prototype in `references/templates/` — that prototype is **retired as a build reference**; its hash-routing/`window` globals/`localStorage` patterns were deliberately not carried into the real app. It's kept only for the neon/pixel visual language (`references/templates/styles.css`: CSS custom properties like `--cyan`/`--magenta`/`--yellow`/`--green`, "Press Start 2P" for pixel headings, JetBrains Mono/Courier Prime for body/mono text).

### Data & backend (Supabase)

SPEC 04 + SPEC 06 replaced all mock data with two public Supabase tables, `games` and `scores` (public read on both, public insert on `scores` only — same trust model the old `localStorage` mock had). Server Components read them via `lib/supabase/games.ts` (`getGameWithScores()`, `getAllGamesWithScores()`); `lib/scores.ts` (`saveScore()`) inserts a run's result. Both are **generic by `game.id`** — adding a new game never requires touching either file. `lib/supabase/client.ts`/`server.ts` are the browser/server SDK clients; `lib/supabase/proxy.ts` backs the session-refresh in `proxy.ts`.

### Game engine contract

Every real game implements the same contract, defined once in `lib/games/engine.ts`:

```ts
export interface GameCallbacks {
  onStateChange(state: { score: number; lives: number; level: number }): void;
  onGameOver(finalScore: number): void;
}
export interface GameHandle {
  setPaused(paused: boolean): void;
  destroy(): void;
}
export type GameFactory = (
  canvas: HTMLCanvasElement,
  callbacks: GameCallbacks,
) => GameHandle;
```

Per-game pattern (established by SPEC 05/ASTEROIDS, repeated for TETRIS/ARKANOID/SNAKE):

- `lib/games/<id>/engine.ts` exports `createXxxGame(canvas, callbacks): GameHandle`. All mutable state lives **inside** the factory closure, never in module-level variables (React StrictMode double-invokes effects in dev, and the player can navigate to/from `/juego/<id>/jugar` repeatedly).
- `components/games/<id>-canvas.tsx` (Client Component) mounts/tears down the engine in a `useEffect` keyed on `restartKey`, and calls `handle.setPaused(paused)` in a second effect keyed on `paused`.
- `lib/games/registry.ts` (`GAME_CANVAS_REGISTRY`) maps `game.id -> canvas component`; `components/game-player.tsx` renders through this registry instead of a hardcoded boolean (that hardcode was retired in SPEC 07).

**Games implemented today:** `asteroids` (SHOOTER), `tetris` (PUZZLE, renamed from `caida`), `arkanoid` (ARCADE, renamed from `bloque-buster`), `snake` (ARCADE, renamed from `serpentina`) — engines under `lib/games/<id>/`, canvases under `components/games/`, both registered in `lib/games/registry.ts`. **Not yet ported:** `gloton` (Pac-Man-style), `invasores` (Space Invaders), `ranaria` (Frogger), `duelo-pixel` (Pong/VERSUS) — no `lib/games/<id>/` folder exists for these yet. Reference material for started/half-built games (where it exists) lives in `references/started-games/`. See also `C:\Users\joses\Documents\Cursos\Dev\claude-code\05-arcade-vault\references\implemented-games.md` when you need to check wich games are implemented and how to implement new ones.

## Workflow: Spec Driven Design

Per `README.md`, feature work follows a spec-driven workflow using `/spec` and `/spec-impl` from the `Klerith/fernando-skills` skills package (installed via `npx skills@latest add Klerith/fernando-skills`, present under the user's `~/.claude/skills/`). Every feature so far (SPECs 01–09 in `specs/`) went through this workflow — check for these commands before starting a non-trivial feature and follow that workflow rather than jumping straight to implementation. Specs are numbered sequentially, kept in `specs/NN-slug.md`, start life as `Status: Draft`, and only get marked `Approved`/`Implemented` explicitly.

## Skills

- Usa siempre `/frontend-design` para diseñar la interfaz de usuario.
- `/add-game` (project skill, `.claude/skills/add-game/SKILL.md`): generates a new SPEC (same format as SPEC 05/06) for porting or designing-from-scratch the real engine of one of the not-yet-ported games above and wiring it into the Supabase leaderboard. It only writes the spec file — never implements code. Run this before starting work on GLOTÓN, INVASORES, RANARIA, or DUELO PIXEL.
- `/spec-impl-game` (project skill, `.claude/skills/spec-impl-game/SKILL.md`): the game-specific variant of `/spec-impl`. Same flow (validate the spec means `Approved`, create the `spec-…` branch, implement step by step pausing for diff review, never auto-commit), plus two additions: it searches `specs/**` recursively so the nested specs from `/add-game` and `game-jam` are reachable, resolves and confirms the spec's `game-id` before touching git, and — once the last plan step is done — chains `skin-designer` and then `mobile-porter`, **one after the other, never in parallel**, asking for confirmation before each. Use it instead of `/spec-impl` whenever the spec ports a game engine or adds a feature to an existing game; use plain `/spec-impl` for everything else.

## Agents

- `game-planner` (project subagent, `.claude/agents/game-planner.md`): decides which game fits the platform best to build next — from the not-yet-ported backlog above or a wholly new concept — evaluating category/color balance, engine reuse, and score-ability. Manual invocation only (`Agent` tool, `subagent_type: "game-planner"`); never dispatch it proactively. It only outputs a recommendation (never writes a spec or code) and maintains its own memory across runs in `references/game-planner-log.md` (full reasoning history) and `references/game-suggestions-todo.md` (pending-suggestions checklist) — read those before assuming what's already been proposed. Run `/add-game <id>` yourself afterward if you want to act on its recommendation.
- `game-jam` (project subagent, `.claude/agents/game-jam.md`): given a theme, designs a game concept and writes at least two `Status: Draft` specs under `specs/game-jam/<game-id>/` (`01-<game-id>-core.md` = full core mechanic + Supabase/registry wiring, `02-<game-id>-<feature>.md` = one complementary feature building on the core), same format as SPEC 07/08/09. The resulting `game-id`/mechanic must always be original — it may take a not-yet-ported backlog game (Glotón, Invasores, Ranaria, Duelo Pixel) as loose _inspiration_ for a theme, but never as a literal port/rename of it; a faithful port of one of those four stays exclusively `/add-game`'s job. Manual invocation only (`Agent` tool, `subagent_type: "game-jam"`, prompt = the theme); never dispatch it proactively. It only writes spec files (never code, never applies Supabase migrations) and has no memory across runs.
- `skin-designer` (project subagent, `.claude/agents/skin-designer.md`): implements the 3 mandatory color skins (`neon`, `retro`, `clasico` = default) for the game(s) named explicitly in its prompt — it refuses to act on any game it wasn't named, and refuses games that aren't ported yet. It edits real code: the shared `lib/games/skins.ts`, a per-game `lib/games/<id>/skins.ts`, the color literals inside `lib/games/<id>/engine.ts`, and a 3-option selector in `components/games/<id>-canvas.tsx`. It never touches `lib/games/engine.ts`, `lib/games/registry.ts`, the player HUD or the CRT frame. Manual invocation only (`Agent` tool, `subagent_type: "skin-designer"`, prompt = the exact game id); never dispatch it proactively. Maintains its own memory across runs in `references/game-with-themes.md`. `/spec-impl-game` runs it automatically as the first half of its post-implementation chain.
- `mobile-porter` (project subagent, `.claude/agents/mobile-porter.md`): audits and fixes the app's mobile/responsive experience (CSS/Tailwind/layout/markup) across the whole app — nav, home, about, biblioteca, salón, auth, and the game HUD/player — treating `specs/10-controles-tactiles-movil.md` (Implemented) as the established convention to respect, not pending work. Note: this repo has no native app wrapper — "mobile app" means this same Next.js app viewed from a mobile browser. Static code review only (no browser/emulation tools) that edits files directly when it finds a clear issue; it never touches `lib/games/engine.ts`, any `lib/games/<id>/engine.ts`, `lib/games/registry.ts`, or the synthetic-event dispatch logic in `components/games/touch-controls.tsx`. Manual invocation only (`Agent` tool, `subagent_type: "mobile-porter"`); never dispatch it proactively. Maintains its own memory across runs in `references/mobile-porter-log.md`. `/spec-impl-game` runs it automatically as the second half of its post-implementation chain, after `skin-designer` has finished.
- `game-performance-booster` (project subagent, `.claude/agents/game-performance-booster.md`): audits and fixes performance issues in the engine (`lib/games/<id>/engine.ts`) of the game(s) named explicitly in its prompt by game-id — it refuses to act on any game it wasn't named, and refuses games without a real engine yet (redirects to `/add-game`). Uses `specs/11-rendimiento-reporte-estado-motores.md` as its baseline reference (the fixed bug: unthrottled `callbacks.onStateChange` calls inside the rAF loop causing ~60 `GamePlayer` re-renders/s — now solved via `createStateReporter`/`EngineState` in `lib/games/engine.ts`) plus a broader checklist (unclamped `dt`, unconditional per-frame array rebuilds, `destroy()` cleanup). It never touches `lib/games/engine.ts`, `lib/games/registry.ts`, `ctx.shadowColor`/`ctx.shadowBlur` or any color/palette decision (that's `skin-designer` territory), or gameplay/collision logic. Manual invocation only (`Agent` tool, `subagent_type: "game-performance-booster"`, prompt = the exact game-id(s)); never dispatch it proactively. Maintains its own memory across runs in `references/game-performance-log.md`.
